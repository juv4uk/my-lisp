знайдено новий архітектурний блокер, якого попередній аналіз не

**Задача:** `OPT-DATA-PARALLELISM` (пріоритет 5.0): "Add rayon-style

## 2. Новий блокер, знайдений цією оцінкою (не в попередньому аналізі)

**`my-lisp/Cargo.toml`'s `[dependencies]` — порожній, буквально
нуль записів.** `rayon` став би першою зовнішньою залежністю
core-крейта за всю історію проєкту.

Але важливіше — перевірено читанням `crates/my-lisp/src/value.rs`:

```rust
pub enum Value {
    String(Rc<str>),
    Symbol(Rc<str>),
    Pair(Rc<Value>, Rc<Value>),
    Closure(Rc<Closure>),
    Macro(Rc<Closure>),
    Builtin(std::rc::Rc<Builtin>),
    ...
}
```

**`Rc` — не `Send`, не `Sync`, за визначенням самого Rust.**
`rayon` вимагає `Send + Sync` для будь-яких даних, що перетинають
потоки. Це означає: паралелізм над `Value`-даними (а це буквально
все — елементи списків, замикання, символи) **структурно неможливий**
без спершу заміни `Rc` на `Arc` **у всій моделі володіння** —
13 місць лише в `value.rs`, 7 файлів по всьому крейту. Другий шар
того самого блокера: `Environment` тримає `Rc<RefCell<Frame>>`
(`environment.rs`) — `RefCell` теж `!Sync` (внутрішня мутабельність
без блокування); навіть після `Rc`→`Arc` знадобився б ще
`RefCell`→`Mutex`/`RwLock` для змінних середовища.

Це не "Складність: середня" — це **окремий, більший рефактор**,
який зачіпає ЯДРО моделі даних усього інтерпретатора, з реальною
ціною: atomic refcounting (`Arc`) і locking (`Mutex`) мають вимірювану
вартість навіть в однопотоковому шляху — саме тому `Rc`/`RefCell`
обрані спершу.

## 3. Чому це справжній блокер, не привід відкласти назавжди

Це не заперечення мотиву з §1 — WSM-24 lишається реальним. Це
конкретизація, ЩО саме треба зробити спершу, чого попередній аналіз
не бачив:

```text
крок 0 (НЕ зроблено, реальний блокер):
  Rc -> Arc в усій Value/Closure/Environment моделі
  RefCell -> Mutex/RwLock у Frame
  виміряти ціну цього ПЕРЕХОДУ САМОГО ПО СОБІ окремо від паралелізму
  (atomic refcounting сповільнює навіть однопотоковий код)

крок 1 (те, що задача просила):
  rayon-based par-map/par-filter/par-reduce поверх кроку 0
```

## 4. Семантичне питання, яке теж треба вирішити (не лише технічне)

Навіть після кроку 0: `map`/`filter`/`reduce` зараз — звичайні
`lib/core.my`-функції з гарантованим детермінованим порядком
обчислення зліва направо. Паралелізація МОВЧКИ зламала б цю
гарантію для будь-якого коду з побічними ефектами (друк, мутація
через замикання над `RefCell`-подібним станом). Той самий інстинкт,
що й уся сьогоднішня розмова про macro hygiene: **явний, окремий
інструмент (`par-map`), не мовчазна підміна наявного `map`** —
opt-in паралелізм, не прихована зміна поведінки того, що вже
існує й на що покладається наявний код.

## 5. Рекомендація

**Не реалізовувати зараз.** Три послідовні кроки, якщо/коли:

1. Окрема задача/ADR: `Rc`→`Arc`, `RefCell`→`Mutex`/`RwLock` в ядрі
   моделі даних — виміряти ціну переходу самого по собі
   (`docs/benchmarks.md`'s наявний harness) до будь-якого паралелізму.
2. Лише після (1): `rayon` як залежність, нові `par-map`/`par-filter`/
   `par-reduce` примітиви — окремі імена, не тиха підміна `map`/
   `filter`/`reduce`.
3. Виміряти на реальному WSM-24-подібному chamfer-навантаженні, чи
   виграш (×N ядер) переважає вартість кроку (1) — не припускати.
