## 1. Найдорожча операція — раціональні дроби

Кожна операція над нетривіальними числами створює BigRational
з купчастим знаменником. Тейлор глибиною 10 на 48 точках =
мільйони цифро-операцій через gcd на кожному кроці.

```lisp
(* 1.5 1.5)   ;; → 9/4 — повноцінний BigRational
(sqrt 2.0)    ;; → 200-значний дріб за 8 ітерацій Ньютона
```

**Фікс:** спеціалізація малих цілих. Якщо p і q влазять в i64,
обчислювати без алокації BigRational. Покриє 90% випадків.
Складність: низька. Ефект: ×2–5 на арифметиці.

## 2. Списки без random access

`nth` ходить список з голови — O(n). Subsample по 4607 точках
через nth = O(n²). Для порівняння форм потрібен O(1) доступ.

**Фікс:** persistent vector (Clojure HAMT) або mutable array
для числових даних. Складність: середня. Ефект: критичний
для научних обчислень.

## 3. Tree-walking інтерпретатор

Кожна ітерація = обхід AST + environment lookup + проміжний Value.
Для chamfer 512×512 це мільйони інтерпретованих операцій.

**Фікс:** компіляція гарячих лямбд в байткод (JIT-тригер:
функція викликана >100 разів). Складність: висока.
Ефект: ×10–100 на гарячому коді.

## 4. Прелоад core.my при кожному старті

`include_str!` + parse при кожному запуску бінарника.
424 функції парсяться щоразу. Для CLI (~50ms) ок;
для батчу з 2220 процесів — ні.

**Фікс:** серіалізований AST snapshot (FASL-файл).
Складність: низька. Ефект: ×5 на старті.

## 5. Відсутність багатопотоковості

Chamfer між двома кривими — ідеально паралелізується.
Зараз один потік.

**Фікс:** rayon-style data parallelism для map/reduce
над великими списками. Складність: середня.
Ефект: ×N на багатоядерних машинах.

## 6. Циклічні посилання протікають

`(def f (lambda () f))` — closure захоплює сам себе через
environment → Rc cycle → витік. Це вже спричинило проблеми.

**Фікс:** Weak references для parent links, або tracing GC
(M0 дизайн готовий у docs/gc-m0-design.md).
Складність: висока. Ефект: усунення класу витоків.

## 7. Number->string не підтримує раціональні

Друк будь-якого неточого раціонального крашиться через
nth з дробовим індексом у digit->string (BUG report 7ad5d02).

**Фікс:** довге ділення в number->string, або
numerator/denominator примітиви в ядрі.
Складність: низька. Ефект: усунення крашів при друку.

## Прогрес 2026-08-24 (Vyasa)

### БОНУС-ВИГРАШ: add/sub без пост-gcd — **67× на rational-chain**
Ідентичність a/b ± c/d = (a·d' ∓ c·b')/(b'·d') при g=gcd(b,d), b=gb', d=gd'
ДАЄ ВЖЕ ЗКОРОЧЕНИЙ результат (класичне доведення через coprimality інваріанту).
Замінено гігантський пост-нормалізаційний gcd чисельника на МАЛИЙ gcd пари
знаменників. warm rational-chain-100: 305ms → **4.53ms** (×67).
Тести: повний крейт 10/10 suites зелених (зміна арифметики = виправданий
повний прогін за resource policy §3). vector-fill ~+13% у тому ж рані —
шлях не чіпано, кваліфікуємо як contention-шум, позначено для наступного заміру.

### Stein GCD A/B — CLEAN RUN 2026-08-24 (same-conditions back-to-back)

Команди: обидва бінарники (Euclid @00b579f worktree-build, Stein @274837b),
nice -n 10 ionice -c2 -n7, timeout 600/ноду, load 4.94→2.27 у процесі.

| n | Euclid | Stein | Δ |
|---|---|---|---|
| 100 | 0.60s | 0.50s | **−17%** |
| 200 | 4.42s | 3.33s | **−25%** |
| 400 | 46.88s | 46.13s | ≈паритет |
| 800 | 416.00s | 412.92s | ≈паритет |

**Висновок:** Stein виграє на малих/середніх n (−17…−25%), на великих n
обидва сходяться до паритету — домінуючою стає вартість великих mul/add
у ланцюзі, не gcd. 

**КОРЕКЦІЯ попереднього [LOAD-CONTAMINATED] запису:** твердження
«n=800 вперше завершився завдяки Stein» було артефактом забруднення —
у чистому A/B Euclid завершує n=800 за 416s (історичний >900s таймаут
був на перевантаженій машині). Реальний ефект Stein: помірний виграш
на малих/середніх розмірах; залишено в коді як суворо краще-or-equal.
