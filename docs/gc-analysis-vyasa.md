# АНАЛІЗ: GC M0 design + holistic map — погляд із траншеї

**Статус:** REVIEW · **Дата:** 2026-08-23 · **Автор:** Оксі (Vyasa)
**Рецензовані документи:** gc-m0-design.md (зовнішній рецензент через
власника, оформив Сакші) · gc-holistic-map.md (Manus AI через власника)
**Позиція рецензента:** я сьогодні написав і ганяв перший великий
обчислювальний workload на цьому інтерпретаторі (WSM-24: 2221 контурів,
точна раціональна арифметика, Тейлорові ряди) — і знайшов 3 баги мови.

**Вердикт коротко:** напрям правильний, тестова доктрина — зразкова.
Але в обох документах недооцінена ціна міграції representation, і є
одне питання, яке треба закрити ДО будь-якого heap: **пояснити
фантомний cdr-баг сьогоднішнього дня.**

---

## 1. Що в документах сильно (приймаю без застережень)

1. **Тестування раніше коду** (M0-design §6, §7, §8): незалежний
   reachability oracle, randomized graph property test, metamorphic
   criterion («stress-режим має давати байт-в-байт той самий результат»),
   MY_LISP_GC_STRESS. Це ідеально збігається з конституційними C7/C10
   та CORE-RULE чесності. Рідко хто пише GC-дизайн, де головний розділ —
   «як це перевірити, не довіряючи самому собі».
2. **Порядок еволюції** (§10): non-moving STW → потім усе інше,
   «не навпаки». Правильно для верифікованості.
3. **Holistic map §23** дає розумну інкрементальну стежку: private
   ManagedHeap для `Pair` only, без змін мовного API.
4. **FPGA-розділ** узгоджений з fpga-lisp: фіксований cons heap +
   названий OutOfMemory — у нас це вже існує як `cons_limit`
   (`Environment::with_cons_limit`) — готовий test seam, варто лише
   підключити до майбутнього колектора.

## 2. Недооцінена ціна: representation migration

M0-design показує цільову модель heap (`Slot`, `ObjectId`,
`HeapObject`), але поточна реальність інша:

```rust
Value::Pair(Rc<Value>, Rc<Value>)
Environment(Rc<RefCell<Frame>>, ...)
Closure { environment: Environment, ... }
```

Весь інтерпретатор, closures, environments, TcpConnection — все
живе на `Rc`. Введення `ObjectId` означає переписання кожного
match-у, кожного клону, кожного Drop-шляху (у Value вже є кастомний
iterative Drop зі stack-safety коментарем). Holistic map §23 це
частково враховує («Pair only first»), але M0-design подає heap-модель
як ніби вона додається поруч. Це найбільший трудовий ризик проєкту і
варто бути названим прямо.

## 3. Найсильніший аргумент ЗА цю роботу — і він не в документах

**Цикли через Rc вже сьогодні протікають.**

```lisp
(def make-adder (lambda (x) (lambda () x)))
```

Closure захоплює environment, environment тримає closure → цикл
`Rc` → звільнення неможливе за refcount. Кожен REPL-користувач,
що створив замикання в сесії, генерує витік. Довгоживучі агенти
(yantra, наші сесії) накопичують такі цикли годинами.

**Пропозиція-передумова (cheap):** перед тим, як писати heap,
додати телеметрію — лічильник створених environments/closures на
сесію + періодичний dump у `(gc-stats)`-стилі. Міряємо: чи цикли
реально виникають у yantra/WSM-24/REPL workload. Якщо так — M0 має
повне право; якщо ні — ми щойно зекономили тиждень роботи.

## 4. Взаємодія з exactness — те, чого нема в документах

Сьогоднішній WSM-24 показав: **найбільший виробник сміття цієї мови —
точна раціональна арифметика**. Тейлорові ряди на раціональних
народжують проміжні дроби з сотнями тисяч цифр (мій 40-кроковий
Ньютон фактично зависав на bignums). M0-design каже: rationals
залишаються «Rust-owned, поза GC». Це означає: найгарячіший
garbage-потік лишається поза колектором і тисне на глобальний
алокатор.

Це свідомий trade-off (раціональні immutable, Rc-clone дешевий),
але його треба зафіксувати в документі як відому діру: workload
«символьна математика з великими дробами» не отримає полегшення від
GC M0. Можливе майбутнє розширення: великі Rational теж в heap
(вони ж — objects з динамічним lifetime).

## 5. Блокер-передумова: фантомний cdr-баг

Сьогодні комбінований файл (lib + brahmanda + 2221 quoted entries)
детерміновано падає з `cdr expects non-empty list` на позиції
quoted-даних, при цьому ті самі дані per-process працюють чисто
(1301 яєць, нуль крахів). Причина невідома.

**Вимога:** пояснити цей баг ДО M0. Якщо це логічна помилка evaluator —
GC нічого не змінить. Якщо ж це якась memory-corruption (маловіроятно
під Rc, але не доведено) — колектор поверх пошкодженого середовища
дасть хибне відчуття безпеки. До того ж metamorphic-тест (§8) може
давати нестабільні результати на багованому evaluator.

## 6. Дрібні зауваження

1. **`(env)` інтроспекція (63a1648) взаємодіє з roots:** snapshot
   тримає клони Values поза heap-структурою — після 2.x ці клони
   мають бути rooted на час життя snapshot'а. Занести в root protocol.
2. **Value::Builtin (2.1)** містить `Rc<dyn Fn>` — сьогодні нічего
   не захоплює, але якщо майбутні builtins закриють Values, їх треба
   rooting-ти; додати в root-чекліст.
3. Holistic map §16 («Persistence is not GC») варто скроссилити з
   нашим knowledge-journal патерном у lib/knowledge.my — та сама
   відмінність, що й між GC та semantic retraction.
