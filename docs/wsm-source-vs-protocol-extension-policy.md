# WSM: виконуване джерело проти протокольного/data-файлу — 2026-08-27

**Статус:** ACCEPTED (пропозиція my-lisp, потребує лише ознайомлення
іншими репозиторіями — не потребує їхньої дії, per §9 федеративної
влади).
**Задача:** `WSM-SOURCE-VS-PROTOCOL-EXTENSION-POLICY` (my-lisp
tasks.my, пріоритет 8.8, без залежностей).
**Зв'язок:** `ECO-DECISION-2026-08-27-MYLISP-WSM-RENAME` (`.wsm` —
канонічне джерело, `.my`/`.lisp` лишаються підтримуваними псевдонімами).

---

## 1. Проблема

`ECO-DECISION-2026-08-27-MYLISP-WSM-RENAME` зробило `.wsm` канонічним
розширенням для **виконуваного** my-lisp джерела. Але екосистема має
й **інший** клас `.my`-файлів — не код, а дані: `tasks.my`, `repo.my`,
`language-contract.my`, `compatibility.my`, `isa-contract.my`,
`evidence/*.my`. Без явної межі рішення WSM-rename міг би (помилково)
трактуватись як "перейменувати все `.my` на `.wsm`" — а це зламало б
реальний, живий, крос-репозиторний протокол, яким користуються
одразу кілька агентів і скриптів.

## 2. Живий стан, перевірений (не гіпотетично)

**Виконувані джерела** (`lib/*.my`, `scripts/*.my`, `tests/**/*.my`) —
парсяться my-lisp-інтерпретатором і **виконуються** як програма:

```
lib/clips-import.my, lib/epistemic.my, lib/meta-eval.my,
lib/knowledge.my, lib/reason.my, ...
```

**Протокольні/data-файли** — парсяться (`read-all`/`read-file`) і
читаються як **дані**, ніколи не виконуються. Знайдено живцем на цей
момент у 7 сусідніх репозиторіях:

```
my-lisp:        tasks.my, repo.my, language-contract.my
tauricode:      tasks.my, repo.my
chess-lisp-zero: tasks.my, repo.my
cml:            tasks.my, compatibility.my
fpga-lisp:      tasks.my, repo.my, isa-contract.my
my-lisp-panini: tasks.my, repo.my
shiva-sutras:   tasks.my, repo.my
```

Плюс `evidence/*.my` — три репозиторії (`my-lisp`, `cml`, `fpga-lisp`)
мають директорію `evidence/`, кожен файл у ній — один запис доказу
(напр. `evidence/G5/my-lisp/6943f51.my`), теж дані, не код.

## 3. Машинно-дієвий тест

Не "людське відчуття", а перевірний критерій, який агент/скрипт може
застосувати до будь-якого `.my`/`.wsm`/`.lisp` файлу:

```text
Файл колись передається інтерпретатору для ВИКОНАННЯ
(`my-lisp <file>`, `eval`, `load`, підключення через lib/ chain)?

  ТАК -> виконуване джерело -> .wsm канонічне, .my/.lisp псевдоніми
  НІ, лише `read-file`+`read-all`/`read-all` як дані -> протокольний
       файл -> залишається `.my`, НІКОЛИ не `.wsm`
```

Другорядний, швидший евристичний сигнал (збігається з першим у всіх
перевірених випадках): протокольні файли завжди лежать у корені
репозиторію під фіксованою, конвенційною назвою (`tasks.my`, `repo.my`,
`language-contract.my`, `compatibility.my`, `isa-contract.my`) або в
`evidence/` — ніколи в `lib/`, `scripts/`, `tests/`.

## 4. Чому протокольні файли НІКОЛИ не переходять на `.wsm`

Різниця не косметична. `.wsm`-перейменування виконуваного джерела —
зворотно сумісна зміна: `.my`/`.lisp` лишаються псевдонімами назавжди
(ECO-DECISION), жоден зовнішній інструмент не ламається.

Перейменування `tasks.my` → `tasks.wsm` — **зламало б протокол**: живі
`swarm-node`-процеси, скрипти синхронізації (`sync-tasks (file
"...")`), і будь-який агент в іншому репозиторії, що читає ці файли за
фіксованою, жорстко заданою назвою (не через розширення-псевдонім, а
через саме ім'я файлу як контракт) — усі зламались би одночасно, у
кожному з 7+ репозиторіїв, без жодної user-facing вигоди (це дані, не
код — нема "виконуваного досвіду розробника", який `.wsm` покращує).

## 5. Правила безпечної міграції

1. **Нові виконувані `.my`-файли** → пишуться одразу як `.wsm`.
2. **Наявні виконувані `.my`-файли** → можна перейменувати на `.wsm`
   опортуністично (не обов'язково, не дедлайн) — `.my` лишається
   робочим псевдонімом назавжди.
3. **Протокольні/data-файли** (`tasks.my`, `repo.my`,
   `language-contract.my`, `compatibility.my`, `isa-contract.my`,
   `evidence/*.my`, і будь-який майбутній файл того самого класу) →
   **завжди `.my`**, розширення НЕ є частиною WSM-міграції взагалі.
4. Новий протокольний файл того самого класу (напр. майбутній
   `capability-manifest.my`) → за замовчуванням `.my`, доки хтось
   явно не обґрунтує інше — консервативний дефолт, не рішення "з нуля"
   для кожного нового файлу.

## 6. Явні non-goals

- **Не масове перейменування.** Жоден скрипт не повинен ходити по
  репозиторіях і масово перейменовувати `.my` → `.wsm` — ні виконувані
  файли (опортуністично, вручну, коли є причина), ні тим більше
  протокольні (ніколи).
- **Не зміна формату протокольних файлів.** Це політика розширення,
  не зміна S-expression-схеми `tasks.my`/`repo.my`/тощо.
- **Не авторитетне рішення для інших репозиторіїв.** Per §9
  (федеративна влада), ця політика — пропозиція my-lisp щодо власного
  іменування, застосовна до всієї екосистеми лише тому, що WSM-rename
  сам був ecosystem-wide рішенням; кожен репозиторій лишається
  авторитетним за власні файли, ця політика лише дає їм машинно-дієвий
  критерій, яким користуватись.

## 7. Наступний крок

Розблоковує `WSM-LINGUIST-ECOSYSTEM-ATTRIBUTES` (GitHub Linguist
`.gitattributes`-класифікація) — тепер є явний критерій, які файли
класифікувати як WSM-мову (виконувані `.wsm`/`.my`/`.lisp`), а які
лишити як generic-дані (протокольні `.my`), замість здогадуватись
по репозиторію.
