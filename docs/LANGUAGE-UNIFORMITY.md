# LANGUAGE UNIFORMITY — однорідність мови

**Статус:** пояснювальний документ (не контракт) · **Дата:** 2026-08-22
**Автор:** Сакші (sākṣī, ox-alpha) · **Звʼязок:** [[PROPOSAL-FIRST-CLASS-BUILTINS]]

---

## 1. Визначення

**Однорідна мова** — мова, де однакові за роллю речі поводяться
за однаковими правилами, незалежно від того, де вони реалізовані
всередині інтерпретатора.

Це пряме застосування G-аксіом: читабельна архітектура замість
прихованої магії. Магія, схована в evaluator'і, порушує принцип так
само, як магія, схована в архітектурі репозиторію.

## 2. Поточна неоднорідність: два світи функцій

```lisp
;; Світ 1: builtin'и (Rust match-гілки evaluator'а)
(+ 1 2)              ;; ✓
(car (list 1 2))     ;; ✓

;; Але як ЗНАЧЕННЯ вони недоступні:
(reduce + 0 lst)     ;; ✗ "unknown symbol: +"
(map car pts)        ;; ✗ "unknown symbol: car"
```

```lisp
;; Світ 2: лямбди (значення середовища)
(def my-add (lambda (a b) (+ a b)))
(reduce my-add 0 lst)     ;; ✓
```

Питання: чим `+` гірший за `my-add`? Для користувача — нічим.
Але evaluator має таємне знання: *«символ у head-позиції → пошукай
ще в спеціальному Rust-реєстрі»*. Це витік інтерпретатора в семантику мови.

## 3. Ціна неоднорідності (evidence WSM-24, 2026-08-22)

1. Шумові обгортки: `(map (lambda (p) (car p)) pts)` — 6 штук в одному
   невеликому файлі геометрії.
2. Пізні помилки: код обчислюється 27 секунд, потім падає на
   `(reduce + 0.0 ...)`.
3. Кожен виклик higher-order вимагає знати, де функція реалізована
   в Rust — витік реалізації в API мови.

## 4. Цільова модель

```text
Було:                              Стане:

symbol у head → Rust registry      symbol lookup → environment
symbol як value → error                  ↓
                                   Value::Builtin | Value::Lambda
                                         ↓
                                   generic apply (один шлях)
```

Special forms (`quote`, `cond`, `lambda`, `def`, `defmacro`, ...)
— окремий клас із синтаксичною evaluation семантикою; вони не стають
callable values. Межа фіксується контрактом.

## 5. Invariant contract 2.1

```text
Any callable that can appear in operator position may also be evaluated
as a value and passed as an argument, unless explicitly classified as a
special form.
```

Acceptance matrix — див. [[PROPOSAL-FIRST-CLASS-BUILTINS]] розділ 8.3.
Ключовий доказ first-classness:

```lisp
(def f +)
(f 20 22)        ;; => 42
```

Shadowing семантика (пропозиція): builtins bootstrap глобальне оточення,
звичайне лексичне shadowing дозволене — мінімум магії.

## 6. Історичний контекст

McCarthy (1960) зробив той самий крок на рівні **даних**: код і дані —
списки → `eval`, макроси, вся потужність Lisp. Contract 2.1 робить
аналогічний крок на рівні **функцій**: усі callable — один тип значення.
Наслідок системний: інтроспекція тривіальна (`(env)`), немає окремих
правил «що можна передавати», нові builtin'и не змінюють правил мови.

## 7. Формула

> Якщо щось поводиться як функція, мова не повинна карати користувача
> за те, де саме в Rust вона була реалізована.

Див. також: changelog запис про 2.0→2.1 у
[[PROPOSAL-FIRST-CLASS-BUILTINS]] розділ 5:
*«2.0 видалив ' reader-macro як філософське рішення; 2.1 робить builtins
першокласними як практичне рішення. Обидва — кроки до однорідної мови.»*
