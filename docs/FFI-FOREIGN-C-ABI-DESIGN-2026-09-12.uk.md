# Foreign C ABI — дизайн (український супровід)

Український супровідний виклад до `FFI-FOREIGN-C-ABI-DESIGN-2026-09-12.md`. Документ фіксує дизайн ДО коду; жодна реалізація не додається разом із ним.

## Контекст: дослідження Guile

Власник дослідив, як Guile взаємодіє з C, і побачив важливий урок для my-lisp: Guile не намагається "знати C-бібліотеки" по одній. Він має ОДИН універсальний міст до C ABI:

```
foreign library handle + symbol address + ABI-сигнатура → callable Scheme procedure
```

`(pointer->procedure return-type function-pointer argument-types)` перетворює адресу C-функції на звичайну Scheme-процедуру — без написання C-обгортки на кожну функцію. Guile також показує дзеркальний напрямок (`procedure->pointer` — Scheme-лямбда стає C callback) і трактує foreign pointer як окремий, суто механічний ресурс з GC-фіналізатором, ніколи не підносячи його до семантичної ідентичності мови.

## Чому це ОКРЕМИЙ трек від Python-моста

Python — окремий рантайм, до якого потрібен транспорт (TCP/subprocess). C-бібліотеки вже завантажувані в процесі — транспорт не потрібен узагалі, лише пряме ABI-виклик. Перевикористання Python-транспорту тут було б передчасною абстракцією — саме тому в репозиторії вже діє принцип "не будувати абстракцію наперед".

## Цільова архітектура

```
MY-LISP → lib/ffi.my (foreign-library-open/symbol/call)
        → мінімальний Rust-субстрат (OS loader + ABI-виклик)
        → .so/.dll/.dylib (BLAS, FFTW, libc, CUDA, ...)
```

## Rust володіє (незвідний механізм)

Відкриття бібліотеки, резолюція символу, реальний виклик C-функції за конкретною calling convention (тут, на відміну від УСІХ інших можливостей, мігрованих цієї сесії, новий Rust-механізм ДІЙСНО виправданий — Rust не може сконструювати довільний C-виклик у рантаймі без чогось на кшталт libffi).

## Lisp володіє (семантична поверхня)

`foreign-library-open`, `foreign-symbol`, `foreign-signature`, `foreign-call`, `foreign-pointer?`, `foreign-library-close` — і КОЖНЕ конкретне прив'язування (`sqrt`, `memcpy`, `blas-dgemm`) живе як звичайний Lisp-код, без жодного нового рядка Rust на нову C-функцію.

## Представлення значення — свідомо НЕ вирішено тут

Дві моделі залишені нератифікованими (аналогічно Decision A Python-треку): (1) opaque-capability-handle як новий варіант `Value` (за зразком `TcpConnection`), або (2) звичайні серіалізовані дані `(foreign-ref N)`, як у Python-треку, із захистом від підробки адреси на боці субстрату. Вибір — перше реальне завдання реалізації (`FFI-002`), не дефолт.

## Явно поза межами v0

Callbacks (`procedure->pointer`), маршалінг структур за значенням, NumericBuffer↔native-memory zero-copy bridge (окремий дослідницький трек `FFI-005` — можливо, важливіший за Python-міст, оскільки в C ABI немає транспортного кордону, що змушує копіювати дані) — і будь-яке конкретне прив'язування бібліотеки, окрім одного proof-of-concept виклику (`libm`'s `sqrt`).

## Задачі

`FFI-001` (цей документ, виконано) → `FFI-002` (вибір моделі значення) → `FFI-003` (мінімальний Rust-субстрат, єдине місце з виправданим новим Rust-механізмом) → `FFI-004` (`lib/ffi.my`, witness через `libm`'s `sqrt`) → `FFI-005` (дослідження zero-copy мосту, окремо від базового механізму виклику).
