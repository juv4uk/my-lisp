## 0. Зміна фрейму (найважливіша частина цієї ревізії)

Початковий план плутав дві різні властивості:

```text
семантичний фундамент     ≠     заборонено перевизначати символ
```

**Недоторканність символу `car`** — властивість parser/evaluator
(чи можна написати `(let ((car ...)) ...)`).

**Семантичний інваріант CAR** — властивість самої мови: операція
`CAR : cons-cell → first-part` завжди поводиться однаково, незалежно
від того, чи символ `car` десь локально затінений, і незалежно від
того, який субстрат (Rust / meta-eval.my / майбутній FPGA) її виконує.

Друге — те, чого власник реально потребує ("я точно знаю, що під
усією системою є 7 речей, значення яких я розумію, можу перевірити і
на які можу спертися"). Перше — окреме, менш важливе дизайн-питання,
яке не варто змішувати з фундаментом.

**Живий доказ, чому їх не можна змішувати**: до Contract 2.1
(2026-08-22) `car` не був first-class значенням — `(map car pts)`
падав з `unknown symbol`, і `WSM-24`-порт на my-lisp писав зайві
lambda-обгортки, щоб обійти це. Захист САМЕ ІМЕНІ заради "чистоти
семи" повернув би цю незручність, не зробивши жодну з семи операцій
хоч трохи надійнішою.

## 1. Нова ціль: Seven Invariant Semantics

```text
CAR   : cons-cell → first-part
CDR   : cons-cell → rest-part
CONS  : (a, b) → cons-cell
ATOM  : value → чи це не cons-cell
EQ    : (a, a) → true (атомна тотожність)
QUOTE : expr → expr, без обчислення
COND  : гілки → обчислюється лише вибрана гілка
```

Ці сім значень не змінюються — символ, що на них указує, може жити в
середовищі, реалізація може відрізнятись між Rust/meta-eval/FPGA,
оптимізації можуть змінюватись. **Семантика — ні.**

```text
            7 semantic invariants
                    │
         ┌──────────┼──────────┐
         ▼          ▼          ▼
       Rust       meta-eval    FPGA
         │          │          │
         └──── conformance ────┘
```

## 2. Що вже реально є (не з нуля)

`crates/my-lisp/tests/mccarthy.rs::implements_mccarthys_seven_primitives`
уже перевіряє шість із семи операцій (немає явної перевірки `cond` у
цій конкретній функції — перевірити й доповнити). Це вже зародок
формального інваріанту, просто не піднятий до названого,
задокументованого статусу й не поширений на всі субстрати.

## 3. План (замість "недоторканність")

1. **Формалізувати й машинно довести** — не просто "тест існує", а
   явний, названий conformance-набір `seven-semantic-invariants`,
   окремий tier у `conformance.my` (той самий поділ core/language/
   ecosystem tiers, що вже є).
2. **Доповнити прогалини**: явна перевірка `cond` (лише вибрана гілка
   обчислюється — перевірити, що НЕ вибрана гілка справді не
   виконується, побічний ефект-тест, не лише значення).
3. **Поширити на всі субстрати** — той самий набір фікстур має
   проходити не лише на Rust-евалюаторі, а на `lib/meta-eval.my`
   (демонстраційному) і, коли дійде черга, на FPGA/CML.
4. **Легка, не жорстка конвенція для shadowing** — не заборона, а
   видимість: якщо код десь затінює одне з семи імен, це мало б бути
   помітно (лінт-попередження чи анотація), не заборонено. Захищає
   від випадкової плутанини, не забирає `(map car pts)`.
5. **Питання "чи забороняти shadowing взагалі" — окреме, пізніше
   рішення**, не частина фундаменту. Може лишитись "ні, і не треба"
   назавжди — це вже нормально, якщо семантичний інваріант
   перевірений і надійний незалежно від цього.

## 4. Явно НЕ зроблено

Жодного рядка коду не змінено цим документом. Contract 2.1 (first-
