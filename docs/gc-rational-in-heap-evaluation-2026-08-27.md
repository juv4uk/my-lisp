# Evaluation: moving large Rationals into a managed heap — 2026-08-27

**Статус:** EVALUATED — рекомендація "не зараз", не implementation.
**Задача:** `GC-RATIONAL-IN-HEAP` (пріоритет 6.0): "Evaluate moving
large Rationals into managed heap. Currently exact rational arithmetic
creates bignum garbage outside GC scope (M0-design keeps rationals
Rust-owned). Taylor series workloads generate massive temporary
rational garbage that global allocator handles but heap could collect
incrementally."

---

## 1. Живий поточний стан (перевірено, не припущено)

**Керованого heap у Rust-крейті ще немає взагалі.** `grep` по всьому
`crates/` на GC/heap-модуль — нуль файлів. `docs/gc-m0-design.md`
(2026-08-23, зовнішній рецензент через власника) — **`Статус: PROPOSED
DESIGN`**, не реалізовано.

`Rational` (`crates/my-lisp/src/value.rs:33`) — `numerator`/
`denominator`, кожен `BigInt` (`crates/my-lisp/src/bignum.rs`),
живе напряму в `Value::Rational(Rational)`, звичайне Rust-володіння
(`Clone`/`Drop`), збирається глобальним алокатором Rust за звичайними
правилами, коли останнє посилання зникає — так, як і каже опис задачі.

## 2. Чому "евальюейт зараз" — передчасно

Питання "чи варто перенести Rational у managed heap" логічно
залежить від того, ЩО ТАКЕ цей heap — а PROPOSED-дизайн, не
реалізація, не дає стабільної відповіді, яку можна оцінювати проти
реального коду. Оцінка "переваги/недоліки" проти неіснуючого API —
спекуляція, не evaluation в дусі §3 кореневого `CLAUDE.md`
(evidence-driven, не "звучить правдоподібно").

**Реальна, перевірена знахідка, що вже частково відповідає на
питання**: сам `docs/gc-m0-design.md`'s начерк (рядок 37) уже
класифікує `Rational` як `Value`-варіант:

```text
Value ::= Nil | Bool | Integer | Rational | Symbol | Ref(ObjectId)
HeapObject ::= Cons(Value, Value) | Lambda {...} | Environment {...} | Vector ...
```

`Rational` стоїть поруч із `Nil`/`Bool`/`Integer`/`Symbol` — НЕ поруч
із `Cons`/`Lambda`/`Environment`/`Vector` (те, що дизайн МАРКУЄ як
`HeapObject`, тобто GC-відстежуване). Це один рядок, ніде глибше в
документі не обговорений і не обґрунтований — але це вже, по суті,
**той самий висновок**, до якого веде ця оцінка, зроблений автором
самого M0-дизайну ще до того, як цю задачу взагалі завели. Варто
підтвердити явно з власником/автором M0, чи це свідомий вибір, чи
недогляд у швидкому начерку.

## 3. Оцінка самого компромісу (для коли M0 таки приземлиться)

Навіть якщо `Rational` стане `HeapObject`-варіантом, `BigInt`
(`numerator`/`denominator`) усередині нього — це `Vec`-подібна
довільно-розмірна структура, яка **у будь-якому разі** виділяється
на Rust-купі, незалежно від того, чи сам `Rational`-хендл
GC-відстежуваний. "Перенести в managed heap" реально означає: чи сам
2-словний `Rational`-хендл (numerator handle, denominator handle)
живе як `Slot` у GC-масиві (mark-and-sweep відстежує його), чи як
звичайне Rust-значення (RC/Drop відстежує його) — не про те, де
живуть самі цифри bignum, це завжди RC-купа Rust.

**За перенесення:**
- Однорідність: усі "великі" об'єкти (cons, lambda, vector, rational)
  проходять один і той самий allocation/collection шлях — простіше
  довести інваріанти GC (сама теза M0-документа: "GC — частина
  семантики машини").
- Паритет із `fpga-lisp`: апаратний heap там реально bounded і
  відстежує все, включно з bignum-подібними структурами — той самий
  G7 (крос-субстратна конформність), який уже мотивував інші рішення
  цієї сесії.

**Проти перенесення:**
- `Taylor series"-навантаження, яке задача цитує як мотивацію
  ("масивне тимчасове rational-сміття"), уже сьогодні коректно
  збирається звичайним Rust-алокатором — RC/Drop не "витікає", просто
  не інкрементальний і не bounded. Немає задокументованого,
  емпіричного випадку, де ЦЕ реально стало проблемою (out-of-memory,
  вимірювана затримка), лише гіпотетичне "могло б бути краще
  інкрементально".
- Додає реальну складність (кожна bignum-операція мусить
  алокувати/звільняти через API M0-heap, не просто `Box`/`Vec`) заради
  вигоди, яку поки нема чим виміряти.

## 4. Рекомендація

**Не реалізовувати зараз** (G4: складність заробляється
продемонстрованою потребою). Три конкретні, послідовні кроки, якщо/
коли це стане актуальним:

1. Підтвердити з автором M0-дизайну/власником, чи рядок 37
   (`Rational` як `Value`, не `HeapObject`) — свідоме рішення чи
   недогляд. Дешево, розв'язує реальну невизначеність.
2. Реалізувати саму M0 GC (окрема, велика задача — mark-and-sweep,
   `ObjectId`/generation, root protocol) — прямий блокер, без якого
   ця задача не має стабільного API для оцінки.
3. Лише після (2): виміряти реальне навантаження (Taylor series чи
   подібне), яке задача цитує, і порівняти empirically — RC/Drop
   проти managed-heap allocation — перш ніж переносити `Rational`,
   не на основі теоретичного аргументу.
