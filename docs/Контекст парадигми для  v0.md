# Контекст парадигми для `epistemic.my` v0

**Призначення цього файлу:** прочитати перед implementation brief.  
**Статус:** пояснення напрямку; цей файл не додає жодної нової API-вимоги, fixture або scope.

> **Guardrail пріоритету.** Якщо цей context і implementation brief здаються суперечливими, implementation brief визначає concrete scope, API та tests v0. Цей файл пояснює намір; він не є підставою розширювати scope через ширшу парадигму.

## Чому існує цей experiment

`epistemic.my` v0 не є окремою «agent feature» і не намагається побудувати scheduler, ontology framework або нову мову. Це маленька перевірка central question:

> **Чи здатна поточна `my-lisp` чесно виразити observation, claim, evidence, intent і capability relation як ordinary data + library code, без зміни kernel?**

Якщо відповідь «так», це є evidence на користь достатньої виразності current kernel. Якщо «ні», потрібен не новий feature за звичкою, а точний semantic-gap report.

## Парадигма `my-lisp`

`my-lisp` тримає small stable kernel і віддає все, що вже можна виразити через S-expressions, functions, macros, persistent structures, existing reasoning та guarded World ingress, у library layer. Convenience не дорівнює semantic gap.

```text
виразити як ordinary data
        ↓
перевірити на реальних fixtures
        ↓
спробувати зламати
        ↓
виявити точний gap, якщо він є
        ↓
лише тоді розглядати narrow extension
```

У цьому experiment не чіпай Rust evaluator, kernel semantics, README, World contract, scheduler/effect system, CML або `fpga-lisp`.

## Важливі межі понять

| Поняття | Що воно означає | Чого воно не означає |
|---|---|---|
| **Observation** | Джерело зафіксувало datum. | Що datum істинний. |
| **Claim** | Хтось пропонує statement для review. | Що statement став fact/proof. |
| **Evidence** | Method і source-ref підтримують, спростовують або не вирішують claim. | Що policy already визнала proof достатнім. |
| **Intent** | Declarative goal, requirements, stop condition і expected output. | Command, plan, scheduler task або execution grant. |
| **World** | Canonical model knowledge-bearing immutable transitions. | Universal state model для lexical env, REPL, process і agents. |

Так само не змішуй різні осі status:

```text
result status:       unknown / partial / blocked / disputed
claim review:        proposed / reviewed / rejected
evidence relation:   supports / contradicts / inconclusive
```

## Capabilities і effects

Agent declaration — це claim. Effective capabilities — host-provided snapshot конкретного environment. `intent-capabilities-satisfied?` порівнює declared `requires` з explicit snapshot і **лише** це.

```text
DATA → VALIDATION → CAPABILITY CHECK → REVIEW → TRANSITION → EVIDENCE
```

Не замінюй цю послідовність прихованим command execution. Intent нічого сам не запускає.

## Provenance та canonicality

Evidence зберігає tagged `source-ref`, але v0 не вдає, що всі source types already можна semantically verify. `source-ref?` is structurally strict and semantically weak.

Semantic evidence і operational receipt різні. First may later enter a reviewed canonical data package. Second includes timestamps, local paths, provider request IDs, costs or agent session details and belongs to audit, not semantic identity. Do not put runtime noise into canonical World data.

Для canonical v0 values має проходити:

```text
read(write-to-string(value)) = value
```

## Єдиний правильний failure mode

Якщо current language/library surface не дає виразити якусь required behavior, **STOP**. Не обходь проблему через прихований primitive, Rust patch або scope expansion. Звітуй лише так:

```text
exact missing capability:
...

minimal witness:
...

why existing primitives cannot express it:
...

candidate minimal extension:
...
```

Потім передай результат на review. Не роби commit або push.
